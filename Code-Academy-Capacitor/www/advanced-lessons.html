Secret 01

Closures: Memory Leaks Nobody Talks About

Everyone teaches "closures remember variables". But 90% of devs don’t know closures can crash your app with memory leaks. Here’s the truth.

The Problem Nobody Mentions

When you create a closure, JavaScript doesn’t just save the variable. It saves the ENTIRE scope chain. If you close over a huge object, that whole object stays in memory forever.

⚠️ Production Bug: I’ve seen React apps leak 500MB RAM because of one bad closure in useEffect. Browser tab crashes after 10 minutes.

The Fix: WeakMap + WeakRef

ES2021 gave us WeakRef. Use it to break the closure chain. This is how Meta prevents memory leaks in Messenger.

Bad Closure - Leaks Memory JS 
function createHandler(bigData) {
  return function() {
    console.log(bigData.user.id); // bigData NEVER garbage collected!
  }
}
Good Closure - No Leak JS 
function createHandler(bigData) {
  const weakRef = new WeakRef(bigData);

  return function() {
    const data = weakRef.deref();
    if(data) console.log(data.user.id);
    // If bigData deleted elsewhere, GC can clean it
  }
}
Pro Tip: Chrome DevTools > Memory tab > Take heap snapshot. Search "Closure". If you see 10MB+ closures, you have a leak.
Secret 02

Event Loop: Microtask vs Macrotask Priority

console.log order isn’t random. There’s a strict priority: Microtasks run before Macrotasks. This decides if your UI updates or freezes.

The Hidden Priority Queue

Most devs think setTimeout and Promise.then run at same time. Wrong. Promise.then = microtask. setTimeout = macrotask. Microtasks ALWAYS run first, even if setTimeout was set to 0ms.

Test This in Console JS 
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

console.log('4');

// Output: 1, 4, 3, 2
// Why? Microtask queue runs before macrotask queue

Why This Matters

If you queue 1000 Promise.then, your UI will freeze. Browser can’t render until microtask queue is empty. Netflix solves this by batching with setTimeout every 50 items.

Secret 03

Proxy: The Invisible Performance Trap

Vue 3 uses Proxy for reactivity. But Proxy is 100x slower than direct property access. Big apps crash because of this.

The Performance Cost

Every time you read obj.name, Proxy trap fires. In a loop of 1 million items, that’s 1 million trap calls. Direct access = 1 CPU cycle. Proxy = 100+ cycles.

Fast vs Slow JS 
// SLOW - Proxy in hot loop
for(let i = 0; i 1000000; i++) {
  sum += proxyObj.value; // Trap fires 1M times
}

// FAST - Cache the value
const val = proxyObj.value;
for(let i = 0; i 1000000; i++) {
  sum += val; // Direct access
}
Rule: Never use Proxy in tight loops. Cache values outside the loop. This one change made Figma 3x faster.
