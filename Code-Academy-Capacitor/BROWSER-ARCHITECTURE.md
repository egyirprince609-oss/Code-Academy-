# Code Academy Browser — Architecture Decision

## Repository facts that determined the design

- The Android package/application ID is `com.wm.codeacademy`; the app uses Capacitor **8.5.3** and its Android target/compile SDK configuration is 36 with minimum SDK 24.
- The native entry is the existing `com.wm.codeacademy.MainActivity`, a `BridgeActivity`; the browser is registered as a local Capacitor plugin rather than by adding a second MainActivity.
- The web source is under `www/`, and the native bundle is generated by `npm run build:native` from `native-src/index.js` through `vite.native.config.mjs`.
- The prior `www/browser.html` browser surface used an `<iframe>` as its page viewport. That did not provide an independent browser engine or a dependable way to display sites which disallow embedding. It has been replaced by a launcher for the native browser in the APK and a clearly labelled system-browser fallback on the hosted/web version.
- Existing Firebase Web SDK initialization/authentication is in `www/authentication.js`, using Firebase Web SDK **10.7.1** and project ID `codeacademybywm`. Its exported `auth`, `db` and `onAuthStateChanged` are reused. No Android `google-services.json` was present; this implementation intentionally does not add a second native Firebase/Google account system.

## Decision: B — a dedicated Android WebView Activity + local Capacitor plugin

The engine is Android System WebView (Chromium-based), provided/updated by Android System WebView or the device's Chrome provider. It is a real browser rendering/network engine, but it is not a full desktop Chromium distribution: supported APIs, codecs, Safe Browsing, TLS roots and rendering behavior depend on the installed provider and Android release.

The official Capacitor InAppBrowser API is useful for presenting external web pages and offers WebView/system/default-browser modes, but it is not a full custom multi-tab browser database/UI. Its documented Android minimum SDK is also higher than this repository's current minimum. Raising the app minimum or trying to layer custom browser controls around that API would not solve local tab/history/bookmark/download/profile requirements. Instead, this patch adds a native screen and a small `CodeAcademyBrowser` Capacitor plugin, compatible with the existing bridge registration pattern.

## Components and data flow

```text
Code Academy Capacitor shell WebView
  ├─ existing authentication.js (Firebase Web SDK 10.7.1; authoritative app session/UID)
  ├─ www/browser.html (native browser launcher + optional sync UI)
  └─ window.CodeAcademyNative
       └─ @CapacitorPlugin(name="CodeAcademyBrowser")
            ├─ BrowserActivity in :browser process
            │    ├─ Android System WebView/Chromium (websites load directly from device)
            │    ├─ BrowserUrlParser (one URL/scheme parser)
            │    └─ BrowserStore (SQLite: tabs/session metadata, bookmarks, history, downloads, settings)
            └─ PrivateBrowserActivity in :privatebrowser process (Android 9+ profile suffix)

Optional sync (only after existing Code Academy Firebase Auth resolves a UID):
  Local SQLite snapshot ←→ browser.html sync coordinator ←→ Firestore
    users/{uid}/browserNativeBookmarks/{recordId}
    users/{uid}/browserNativeHistory/{recordId}     [explicit history opt-in only]
    users/{uid}/browserSettings/nativePreferences
```

The WebView that renders arbitrary websites is in a distinct Android process and uses its own WebView data directory suffix on API 28+. Normal browser site data is retained for the same local profile, but cookies/local storage/cache are cleared before loading sites after a Code Academy profile/UID switch so one account does not inherit the prior profile’s website login state. It cannot navigate or replace the main Code Academy shell WebView. The plugin has no remote-site JavaScript bridge.

## Engine and lifecycle

1. The existing `menu.html` opens `browser.html`; native APKs auto-open the native browser only after the existing Firebase Auth state resolves. If that state is still pending, the launcher waits instead of silently selecting the wrong device-local profile; if the auth module errors, local device-profile browsing is made available. Settings uses `browser.html?settings=1`. The direct controls remain available if auto-open is unavailable.
2. The native plugin starts `BrowserActivity` with the current Firebase UID as a **local profile partition key only**; Firestore authorization still depends on `request.auth.uid` rules. Signed-out use uses a device-local profile.
3. Android WebView performs DNS, IPv4/IPv6 selection, connections, HTTP redirects, HTTPS certificate validation and TLS through Android's network stack. Code Academy does not proxy or relay page traffic and does not run a custom DNS resolver.
4. Each tab has an ID and saved current URL/title/navigation metadata. Up to 12 logical tabs are retained and at most 3 WebViews remain live; additional tabs can be evicted and restored by reloading their saved URL. JavaScript execution/form state cannot always survive process death or eviction.
5. Tabs/session metadata is saved to SQLite away from the UI path. Back returns through WebView navigation, closes a tab when appropriate, or finishes the browser Activity to return to the preserved app shell.
6. File uploads use Android's document picker; downloads use Android `DownloadManager`; WebView camera/microphone/location requests prompt in-app and Android permission consent. No untrusted filesystem paths are exposed.

## Local schema

`BrowserStore` is SQLiteOpenHelper schema version 3. Tables: `bookmarks` (UUID ID, URL/title/domain/folder, create/update times, deleted tombstone), `history` (UUID, URL/title/domain, visit/update time and tombstone), `downloads` (source URL, suggested filename, MIME, DownloadManager ID, status/URI/size/error) and `settings` (key/value/update time). Schema migrations 1→2 add history tombstone/update columns and 2→3 add download byte-progress columns without dropping prior records. Active history is capped at 1,000 rows; download display is capped at 300. SQLite database filename includes a hash of the local profile ID so the account profiles do not reuse the same local metadata database.

The active tab/session metadata is saved in profile-namespaced SharedPreferences. Tab content itself is restored by URL rather than promising a byte-for-byte WebView restore. No passwords, form bodies, cookies or raw HTML are stored in browser tables.

## Cloud schema and merge

- Bookmarks: `users/{uid}/browserNativeBookmarks/{uuid}`.
- History: `users/{uid}/browserNativeHistory/{uuid}` only when the local setting `historySyncOptIn=true`.
- Settings: `users/{uid}/browserSettings/nativePreferences`.

Record IDs are stable UUIDs. Deletes for bookmarks and history are normally represented as `deletedAt` timestamps and `updatedAt` changes. Sync fetches in bounded 200-document pages and writes in batches of at most 400; records merge by greatest `updatedAt`, with deterministic serialized-record tie-break. Local records survive offline/sync failure and are retried on reconnection/visibility. Firestore Web SDK cache persistence is attempted and its unsupported/multi-tab failure is tolerated. An explicit “Delete cloud browser data” action is separate: it removes these cloud collections/documents and pauses sync to prevent the device's retained local records from immediately being uploaded again.

The application must deploy and test the supplied rules add-on merged with its real canonical rules. There was no canonical `firestore.rules` in the inspected archive, so this ZIP does not claim live Rules deployment. History read/write is intentionally not run while the sync opt-in is off; prior cloud history remains until explicit cloud deletion.

## Auth and identity

`www/authentication.js` remains authoritative for Code Academy sign-in (Firebase Web SDK 10.7.1, Firebase project `codeacademybywm`, exported `auth/db/onAuthStateChanged`). The inspected module implements email/password signup and login, Google sign-in (the active `signInWithGoogle()` path uses `signInWithPopup`; a redirect-result helper is also present), and phone OTP using `signInWithPhoneNumber` plus a reCAPTCHA verifier. No Facebook/GitHub/Yahoo provider implementation was found in this module. No browser-specific login was added. The browser native Activity does not claim to share a native Firebase SDK in-memory user. Instead, the JS shell passes the current UID only to partition its local SQLite snapshot; all cloud operations happen in the layer already owning Firebase JS Auth. Rules must independently authorize that UID against the authenticated request. Native Google Credential Manager flow is not introduced because the app already has a Firebase Web Auth flow and the project has no `google-services.json` or verified native OAuth setup.
